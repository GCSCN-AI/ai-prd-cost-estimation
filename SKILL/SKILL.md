# AI 软件规模与复杂度评估

本 Skill 用于在需求阶段或设计阶段，对软件的功能规模、业务复杂度、不确定性、交付条件和单位生产率进行可追溯评估。模型是证据抽取、候选判断和风险发现助手；系统边界、计量单位、权重、系数、公式和最终批准必须由版本化规则与具名评审人负责。

## 适用范围与门禁

方法适用于企业管理软件，以及具有明确业务流程的 B2C/B2B2C 软件。适用项目必须通过以下门禁：

| 门禁 | 必须有的证据 | 不通过示例 |
| --- | --- | --- |
| `G1` 业务目的 | 组织经营、管理、运营、合规或对外业务流程；或消费者参与的交易、预约、服务交付、订单履约、活动运营流程 | 只展示内容、提供个人工具或进行娱乐 |
| `G2` 业务对象与动作 | 客户、订单、采购、预约、报价、商品、场地、活动、资产、工单、审计记录等对象，以及创建、提交、审批、确认、取消、履约、查询或变更动作 | 只有静态页面、自由创作、单机玩法或通用编辑 |
| `G3` 参与者与责任 | 至少两个可识别参与者，或消费者与商家/运营/服务提供方；责任、授权或交付关系可定位 | 只有匿名浏览者，或单一用户且无业务责任关系 |
| `G4` 系统边界 | 可声明系统边界、排除项和业务/运营责任主体；混合产品可隔离独立交付的业务子系统 | 只有平台愿景，无法区分产品、外部服务和实现资产 |
| `G5` 领域适配 | 主要工作量由业务规则、工作流、交易、状态、记录、库存、容量、排班、权限或运营约束驱动 | 开发者/工具软件、纯内容或社交、游戏、媒体/创意、嵌入式/实时控制、科学计算、基础设施或平台软件 |

只有 `G1`～`G4` 全部通过且不触发 `G5` 排除项，门禁才是 `pass`。B2C 不因消费者入口自动排除，但必须存在消费者与商家、运营方或服务提供方之间的可观察业务流程。混合产品先隔离可独立交付的业务边界；无法隔离时返回 `not applicable`。

门禁记录必须保存：产品目的、参与者与责任主体、业务对象和动作、系统边界、排除范围、逐项证据、评审人和日期。门禁失败后停止计算，不输出 `US`、`C`、`CF`、`D`、`V`、`AS` 或 `P`，也不以参考值绕过停止规则。

## 证据与输入边界

评估开始前冻结输入文件、版本或提交号、文档角色、项目阶段、系统边界和排除项。区分正式 PRD、设计文档、概念说明、能力清单、测试夹具和实现资产；概念说明只解释背景，测试、图片、CSV、JSON、种子数据和页面数量不直接计入功能规模。

每条证据只使用以下状态：

- **Observed**：原文直接支持，可定位到版本和位置。
- **Assumed**：为计算采用的明确本地约定，必须写出约定内容。
- **Unknown**：评估所需但资料没有给出的信息，进入待确认清单。
- **Rejected**：相关但被计数边界排除的内容，例如测试条数、页面数量或实现库数量。

为区分能力宣称和可计量功能，使用三个证据等级：

- `E0`：只有能力或页面描述，没有参与者、触发条件和业务结果。不进入 `US`。
- `E1`：有业务参与者、触发条件和业务目标/结果，可进入 provisional UUCP；缺少字段级输入、输出或读写证据的部分标为 `Assumed`。
- `E2`：在 `E1` 基础上还有输入/输出、数据交互和验收条件，可按观察证据计量。

每个功能过程至少保存 `id`、`source`、`citation`、`actor`、`trigger`、`outcome`、主路径、主要替代路径、数据交互、验收条件、计量单位、候选权重、证据等级、证据状态、置信度和评审决定。建立“需求条目 → 功能过程 → 设计/数据/接口证据 → 验收条件或测试场景”的追踪矩阵。没有对应功能过程的需求条目进入 `Unknown` 或澄清清单。

当输入是含多个直接子文件夹的目录时，进入批处理模式：逐文件夹执行门禁和完整评估，保留独立账本与结果；不得跨项目相加功能规模或成本，只能在各项目完成后作比较排名。

## 主计量单位与确定性计算

每个项目只选一个主计量单位，不同单位只能交叉检查，不能相加：

| 输入证据 | 主方法 | 使用边界 |
| --- | --- | --- |
| Actor、用户目标、用例和事务叙述，缺少字段级细节 | UCP/UUCP | 按用户目标分组，不把控件或页面当成用例 |
| 可逐项识别 ILF、EIF、EI、EO、EQ | NESMA/IFPUG | 统一采用一种成熟度和计数规则 |
| 功能过程明确包含 Entry、Exit、Read、Write | COSMIC | 只计声明的软件边界内的数据移动 |
| 只有能力条目，没有交互叙述 | provisional UUCP | 事务档位标为假设，置信度保持低 |

本 Skill 的 PRD 案例默认采用 provisional UUCP。简单、平均、复杂用例分别计 `5/10/15`；`UAW` 按 Actor 复杂度计分：人类 Web 角色 `3`，文本或协议型外部参与者 `2`，自动化或简单外部服务 `1`。同一主体承担多个业务责任时分别记录；仅浏览不计 Actor。

```text
UUCW = 5S + 10A + 15C
US   = UAW + UUCW
AS   = US × CF
P    = AS × (C / C') × D × V
```

其中 `US` 是未调整主规模，`AS` 是不确定性调整规模，`C'` 是历史项目平均复杂度，`D` 是经批准的交付因素，`V` 是量纲与公式一致、经过验证的复杂度归一化单位工作量或单位成本因子。若组织历史资料记录的是生产率倒数，必须先按版本化规则换算为公式所需因子。完整 UCP 的技术和环境因子只有在组织拥有相应数据并批准规则时才能使用。模型不得修改档位定义、将 UUCP 与功能点相加，或把测试步骤当成功能过程。

## 复杂度 `C`

只对需求或设计已确认的约束评分。按 `L/W/D/A/I/Q/O` 七个维度以 0～5 分评分，使用 [references/scoring-rubric.md](references/scoring-rubric.md) 的锚点和最低证据包。通用交易型系统的权重为 `0.25/0.20/0.15/0.15/0.10/0.10/0.05`，顺序对应 `L/W/D/A/I/Q/O`：

```text
C = 0.25L + 0.20W + 0.15D + 0.15A + 0.10I + 0.10Q + 0.05O
```

未知证据不得静默记为零。只有评审人确认某维度在声明边界内确实不存在，并且不存在待确认外部依赖时，才可按该维度得分 0；否则保留为 `Unknown`，暂不发布完整点值。已经计入 `C` 的证据不得再次进入 `CF`；未决因素不得提前作为 `C` 高分。

## 不确定性、交付和生产率

### `CF`

用 `CF = f(M, R)` 表示不确定性：`M` 选择基础区间，`R` 是风险登记表，负责人按风险影响选取区间内值。文档成熟度帮助选区间，但不等于置信度：

| 阶段 `M` | 证据状态 | `CF` 候选区间 |
| --- | --- | ---: |
| `M0` 概念说明 | 目标和范围仍在讨论 | 1.50～2.00 |
| `M1` PRD 草稿 | 用户目标存在，边界和验收不完整 | 1.50～2.00 |
| `M2` 结构化 PRD | 功能过程有记录，尚无设计评审 | 1.26～1.50 |
| `M3` 设计评审通过 | 状态、接口、部署和非功能要求已确认 | 1.00～1.25 |
| `M4` 迭代基线 | 需求稳定且有迭代速度数据 | 1.00 |

`R` 至少覆盖六类风险：范围和边界、验收条件、外部接口和供应方、数据模型/权限/组织隔离、性能/可用性/合规、版本/迁移/部署。每条风险保存引用、影响的 `US` 或 `C` 维度、影响等级、责任人、关闭日期和是否已经计入 `C`。六类风险均已检查且无开放高影响风险时取区间下段；存在有责任人和关闭条件的中高风险时取中段；存在无责任人或关闭条件的高风险，或风险登记缺失一类以上时取上段。

### `D`、`V` 与 `P`

`D` 只在拥有技术栈、团队能力、平台复用资产、部署范围、质量门禁和平台边界证据时评估；模型只能将需求匹配到版本化能力目录，不能从宣传文字推导系数。关键判断应由小型原型和实际部署、测试、迁移、运维人日验证。

`V` 只使用统一规模口径的历史项目或明确标注的外部基线。历史数据需规范化范围、实际人日/成本、团队、技术栈、质量门禁、交付范围、变更、返工、缺陷和 AI 使用情况，并按时间切分留出项目回测。没有数据时标为不可评估或 provisional baseline，不以代码量作为通用生产率代理；不同量纲或未经校准的生产率不得直接代入 `P`。

没有经验证的 `D` 或 `V`，`P` 不可评估，不生成费用或报价。

## AI 职责、风险与验证

AI 可以：抽取带引用的 Actor、功能过程和复杂度证据；提出 `E0/E1/E2`、档位和维度评分候选；发现重复、遗漏、未知项和风险；维护追踪矩阵；清洗历史数据、召回相似项目和做敏感性分析。

AI 不可以：决定系统边界和门禁、把未知变成零、修改权重或系数、同一证据在 `C` 与 `CF` 重复计费、直接发布单点成本或替代具名审批。

| 参数 | 主要风险 | 验证要求 |
| --- | --- | --- |
| `US` | 合并角色、误计示例/测试、拆分漂移 | 两名评审人盲评建立金标准；比较 Precision、Recall、F1、引用正确率、重复率、`US` 偏差和重跑稳定性 |
| `C` | 把未写当成没有、同一证据重复计费、把风险算入复杂度 | 独立评分；检查七维最低证据包、逐维 MAE、重复计费和加权敏感性 |
| `CF` | 压低未知项，或把已确认约束再次加价 | 项目负责人确认 `M`；六类风险登记；按规则表选区间；按时间顺序回放需求变更 |
| `D` | 目录过期，把组件存在误判为无需集成 | 关键原型确认原生/扩展/外部服务，再与实际交付数据对照 |
| `V` | 样本偏差、范围混杂、信息泄漏、遗漏返工缺陷 | 时间切分留出回测，报告 MAE、区间覆盖率和分组误差 |
| 权重、系数、公式、报价 | 模型改写政策或直接承诺结果 | 只能从批准的版本化规则和统计模型读取，具名负责人批准 |

## 置信度与验证门槛

置信度是证据和验证判断，不是模型自报概率。按参数分别记录证据覆盖率、假设率、未知率、边界稳定性、评审一致性、固定配置重跑稳定性和验证强度，并采用最弱环节原则：

```text
Conf_US = min(证据覆盖、边界稳定、评审一致、重跑稳定、参数验证)
Conf_C  = min(维度证据、锚点校准、评审一致、重复计费检查、重跑稳定)
Conf_CF = min(阶段确认、风险登记完整度、负责人批准、历史回放、C/CF 分离)
Conf_AS = min(Conf_US, Conf_CF)
Conf_P  = min(Conf_US, Conf_C, Conf_D, Conf_CF, Conf_V)
```

“高/中/低”是序数等级，不对应概率。`US` 和 `C` 达到“中高（受限）”至少要求：计数或评分项 100% 有引用、明确假设或批准的不适用判断；`US` 的 `E1/E2` 追踪覆盖 100%；`C` 七个维度都有最低证据包或批准的不适用判断；重复计费为 0；两名评审人 `US` 相对差异不超过 10%，`C` 逐维绝对差异不超过 0.5；固定配置重跑时 `US` 变化不超过 5%、`C` 变化不超过 0.25。缺少完整历史回测时只能标为“中高（受限）”，不能标为高。

`CF` 达到“中”至少要求项目负责人确认 `M`，六类风险均已检查，高影响风险有责任人和关闭条件，取值可由规则表重放，并完成至少一轮按时间顺序的需求变更回放。区间覆盖率阈值由组织校准，启动值可取 80%，不是行业常数。

## 工作流程

1. 执行 `G1`～`G5` 门禁，记录证据、边界、排除项和评审人；失败即停止。
2. 冻结输入版本和阶段，运行 `scripts/inventory_markdown.py` 检查 Markdown 标题、列表和表格，声明缺少的设计、部署或历史数据。
3. 建立证据账本和需求追踪矩阵，标注 `Observed/Assumed/Unknown/Rejected` 与 `E0/E1/E2`。
4. 选择一个主计量单位，闭合功能过程清单，确定性计算 `UAW`、`UUCW`、`US` 和 `AS`。
5. 按七维锚点评估 `C`，为每个维度保存最低证据包、未知项和评审决定。
6. 由负责人依据 `M` 和风险登记表确定 `CF`；有平台和团队证据才评估 `D`，有规范化历史数据才评估 `V`。
7. 从账本重放公式，执行覆盖率、重复计费、双人差异和固定配置重跑检查。
8. 输出范围、逐参数置信度、风险、待补证据、模型/提示词/规则版本和具名审批点。任何输入、边界、规则、接口、权限、部署或验收变化都触发重新评估。

## 输出契约

输出顺序固定为：

1. 适用性门禁及排除范围。
2. 输入边界、文档角色、阶段和成熟度。
3. 主计量方法、单位和被拒绝的替代方法。
4. 功能过程账本、证据等级和 `US` 计算。
5. 七维复杂度证据、未知项和 `C` 计算。
6. `D`、`CF`、`V` 的状态、假设和风险。
7. `AS = US × CF` 及经批准的成本公式；不可评估项明确写出原因。
8. 验证检查、逐参数置信度、范围、责任人和审批点。

使用 [references/scoring-rubric.md](references/scoring-rubric.md) 的锚点、门槛和公式；使用 [references/output-template.md](references/output-template.md) 生成评估记录。不要修改 PRD 或设计源文件；除非用户明确要求生成文章或报告，否则将账本和结果保存为独立产物。
